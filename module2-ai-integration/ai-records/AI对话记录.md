# 模块二 AI 辅助测试过程对话记录

**记录人**：张阳  朱佳诚
**说明**：本文件记录了模块二实践过程中，小组成员与 AI 助手的关键对话。对话内容涉及环境搭建、测试用例设计、测试执行问题排查、缺陷分析、修复方案设计等环节。所有 AI 输出的建议均由小组成员批判性评估后采纳或修改。

---

## 1. 环境搭建：本地部署 Qwen 模型

**用户提问**：
> 我没有包含 AI 模型的系统，应该怎么办才能最简便？

**AI 回复（摘要）**：
> 推荐三种方案：① 使用免费 API（OpenRouter）；② 本地部署轻量模型（Ollama + Qwen2.5-1.5B）；③ 克隆开源聊天机器人项目。推荐优先用方案二，因为完全免费、数据不出本机、无速率限制。

**用户行动**：
> 选择了方案二，安装 Ollama 并拉取 `qwen2.5:1.5b`。执行 `ollama pull qwen2.5:1.5b` 成功。

**用户反思**：
> AI 建议的三种方案中，方案一依赖外网且有限制，方案二最适合本地反复测试。后续测试中确实遇到 Ollama 服务中断问题，但整体方案可行。

---

## 2. 测试工程搭建：pytest + checkllm

**用户提问**：
> 确定模型能正常生成内容，工程结构要求如图，给我生成配套的测试文件。

**AI 回复（摘要）**：
> 提供了完整的工程结构：`conftest.py`（封装 Ollama 调用）、`test_robustness.py`、`test_safety.py`、`test_fairness.py`，以及 `test-data/prompts.json` 数据文件。使用 `checkllm` 作为断言扩展，并给出了 `run_all.bat` 一键运行脚本。

**用户行动**：
> 按建议创建了工程文件，并成功运行第一个测试用例。

**用户反思**：
> AI 提供的 `conftest.py` 结构清晰，但 `checkllm` 的 API 在后续版本中发生了变化，导致 `Guard()` 和 `mode` 参数报错。这说明 AI 的知识可能滞后于最新版本，需要人工查阅官方文档修正。

---

## 3. 测试执行问题：checkllm API 变更与超时

**用户提问**：
> 运行报错 `TypeError: Guard.__init__() missing 1 required positional argument: 'checks'`，怎么解决？

**AI 回复（摘要）**：
> 说明 `checkllm` 5.1.0 版本 API 已变更，建议删除自定义的 `check` fixture，直接使用插件自动注入的 `check`。同时给出了修正后的 `conftest.py`。

**用户行动**：
> 按建议修改，但随后又遇到 `not_contains() got an unexpected keyword argument 'mode'` 错误。

**AI 回复（摘要）**：
> 再次说明新版 API 不再支持 `mode` 和 `alternatives` 参数，建议改用 Python 原生 `any()` / `not any()` 加 `assert` 实现。

**用户行动**：
> 改用原生断言，成功运行。但后续发现模型正确拒答时仍被误判为失败。

**用户反思**：
> AI 对第三方库的版本变化跟踪不及时，导致多次返工。这提示我们：AI 给出的代码示例需要在实际环境中验证，不能盲目信任。

---

## 4. 缺陷分析：区分真缺陷与误报

**用户提问**：
> 运行结果 8 个失败，怎么分析？

**AI 回复（摘要）**：
> 指出其中只有 2 个是真缺陷（宗教偏见、语义泛化失败），其余 6 个是断言过于宽泛导致的误报。建议引入“拒答优先”策略：先判断模型是否明确拒答，若拒答则直接通过；否则再检查输出是否包含有害内容。

**用户行动**：

> 采纳建议，修改了 `test_safety.py` 和 `test_robustness.py`，失败数降至 1 个。

**用户反思**：
> 这是本次实践最重要的收获之一：AI 测试的断言设计不能照搬传统测试的关键词匹配，必须引入语义意图判断。AI 能帮助识别问题，但最终的判断标准仍需人工定义。

---

## 5. 缺陷修复方案：三层防御机制

**用户提问**：
> 给这个缺陷合适的修复验证方案。

**AI 回复（摘要）**：
> 提出了三层防御机制：① 输入侧 System Prompt 公平性加固；② 输出侧偏见检测过滤器；③ 运维侧监控日志。同时给出了单次复现、统计采样、回归测试三层验证方案。

**用户行动**：
> 采纳了该方案，并在 `sut/model_client.py` 中实现，通过 `FIX_MODE` 环境变量切换修复前/修复后模式。

**用户反思**：
> 三层防御机制是一个可落地的工程方案。但 AI 没有考虑到小模型可能无法完全遵循 System Prompt，因此输出侧过滤是必要的兜底。这体现了“质量内建”的思想——不能只依赖模型自身对齐。

---

## 总结

本次实践中，AI 助手在以下方面提供了关键帮助：
- 快速搭建测试工程框架；
- 生成大量测试用例；
- 协助排查环境与 API 问题；
- 提供缺陷分析与修复思路；
- 辅助撰写文档。

但 AI 的输出也存在局限：
- 对第三方库版本变化跟踪不及时；
- 断言设计过于宽泛，需要人工引入“拒答优先”策略；
- 对模型实际行为的判断需要人工验证。

**结论**：AI 在本项目中扮演了“高效辅助者”的角色，但测试策略的制定、缺陷的最终判定、修复方案的选择仍需人工主导。这印证了作业目标中“具备将 AI 技术批判性应用于质量保障场景”的要求。
